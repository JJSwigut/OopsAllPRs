# Core Logging and Train Choice Verification

Date: 2026-09-21. Local, uncommitted work in `swiggy/launch-integration`; no public release, telemetry, purchase attempt, store change, or persistent user-data change.

## Audit Steps

1. **Train with saved templates:** the previous screen had a large empty upper region. A template was an implicit whole-row launch target while the prominent action started an empty workout. See `build/smoke/core-logging/before/02-train.png`.
2. **Template launch and logging:** a temporary nine-free-workout fixture opened `Demo: Progress Push`; prior values loaded into the focused Bench Press set, then the exercise picker exposed recent exercises, search, custom creation, and clear Add actions. See `before/05-active-template.png` and `before/06-picker.png`.
3. **First persisted set:** logging Bench Press created a granular PR and started the workout timer. Android then requested notification permission for the persistent rest surface. See `before/07-after-log.png`. This is a genuine mid-workout interruption risk, not a claim that the underlying rest timer failed.
4. **Explicit reuse choice:** Train now leads with `Train` and an explanatory line. Each saved template exposes Start, Edit, and Delete under its name; the separate primary action says `Start empty workout`. See `after/05-final-train.png`.
5. **Large-text check:** at 320dp width and 130% text, template names, metadata, and actions remain horizontal and readable. The first implementation made names collapse into one letter per line; the accepted layout uses a full-width row with an action line beneath. See `after/03-small-train-fixed.png`.
6. **Clean debug-install path:** debug seeding intentionally creates ten history workouts. That had exhausted the normal free-workout ledger and blocked `Start empty workout` behind a disconnected Play purchase surface. A newly seeded developer demo now receives local developer access only after the seed loads; release builds do not create developer seeds or receive this access. The clean debug install now reaches the empty active-workout state. See `after/07-debug-empty-active.png`.
7. **Empty workout wording:** the initial active-workout card now confirms that the workout is ready while the fixed bottom action remains the single `Add exercise` command. This removes duplicated command wording without changing the focused logging flow.
8. **Store recovery wording:** unavailable purchase offers now use one customer-facing recovery message and retain the Retry and Restore actions. Matching raw platform errors are suppressed rather than repeated beneath the actions; distinct errors remain visible.
9. **Top-level live audit:** API 35 reviewed History, Progress, and Profile on the preserved 19-workout baseline. History initially exposed anonymous raw ISO timestamps; it now renders the leading exercises, such as `Bench Press + Cable Triceps Extension +2`, and a local readable date/time. See `after/08-live-train.png` and `after/09-history-recognizable.png`. Progress surfaced recent achievements and the evidence ladder without overlap (`after/10-live-progress.png`). Profile was observed both while loading the offer and after its disconnected-store result; the final unavailable state is one customer-facing recovery message plus Retry and Restore (`after/13-profile-friendly-store-error.png`).
10. **Progress date consistency:** Progress evidence initially used raw ISO dates such as `2024-07-03`, even though the History surface had moved to readable local dates. The shared short-date formatter now applies the viewer's local timezone and presents compact month/day labels. See `after/14-progress-friendly-dates.png`.
11. **Routine builder hierarchy:** API 35 revealed that an inline rest-duration roller dominated a newly added exercise card, hiding its planned set fields below the first viewport. Rest is now a compact summary with a dedicated change dialog, leaving the set kind and target fields visible. Template targets now say `Target reps`, `Target kg`, and `Target time`, rather than incorrectly implying prior performance. See `routine-editor/07-target-fields.png` and `routine-editor/08-rest-dialog.png`.
12. **First-run Train path:** the production code path was locally assembled, signed only with the local debug certificate for emulator installation, and launched from cleared app data. It contained no developer seed data, showed the direct `Start workout` / `Create routine` choice, and reached the empty active-workout state without a purchase interruption. See `first-run/01-empty-train.png` and `first-run/02-empty-active-workout.png`.
13. **Focused-workout navigation:** the old `Close` action had two different effects: it returned from a focused exercise to the exercise overview, or dismissed the workout from that overview. A focused exercise now exposes `Exercises`; selecting it shows the exercise overview, where the separate `Close workout` action is available. API 35 semantics and screenshots confirmed both states using a temporary local fixture. See `active-top-action/01-focused.png` and `active-top-action/02-overview.png`.
14. **Profile export choice:** Profile previously put four equal export buttons directly in the scrolling settings surface, without explaining which file to choose. It now presents one `Export data` command with a concise explanation and a separate choice dialog for Workouts, Routines, Exercises, or Personal records. API 35 verified the compact entry and every choice in the dialog. See `profile-audit/05-export-entry.png` and `profile-audit/06-export-picker.png`.
15. **Prior-value provenance:** adding an exercise reuses compatible values from the last completed workout, but previously gave no indication that the numbers were suggestions rather than a routine target. The untouched draft now says `Last logged values`; any direct edit removes that hint. API 35 verified the prefilled Bench Press state and an incremented rep value with the caption removed. See `prefill-provenance/02-prefilled.png` and `prefill-provenance/03-edited.png`.
16. **Completed-workout date consistency:** the completed-workout detail still exposed a raw local ISO date even after the History list had moved to friendly local dates. It now shows a compact local day and date, such as `Tue, Jul 2`, with timezone-boundary regression coverage. API 35 confirmed the detail after selecting a history item. See `summary-audit/02-summary-local-date.png`.
17. **Fresh completion receipt:** an ordinary successful finish had no visible saved confirmation; `Workout saved.` appeared only when a post-commit warning existed. The receipt is now always shown after a committed finish, with any warning appended when necessary. API 35 completed a temporary one-set workout and displayed the receipt before the completed-workout detail. See `completion-receipt/04-saved-receipt.png`.
18. **Completion-to-progress route:** the completed-workout screen now offers `View progress` next to the optional template and edit actions. It selects the existing Progress destination and its evidence-backed Capability and Work capacity readings; it does not add a new score or change PR rules. API 35 confirmed the action and selected Progress state. See `summary-progress/01-summary-action.png` and `summary-progress/02-progress.png`.
19. **Template-save handoff:** saving a completed workout as a template now leaves an explicit `Open in Train` action beside the saved-template receipt. It clears the completed-workout detail before selecting Train, where the saved template is visible and ready to start. Once saved, the duplicate `Save as template` action is removed, leaving only meaningful follow-ups. A long template name is presented full width with `Open in Train` on its own line, avoiding collision at 320dp and 130% text. API 35 saved temporary templates, opened Train, and confirmed the template row, the post-save action hierarchy, and the constrained layout. See `template-handoff/saved.png`, `template-handoff/train.png`, `template-handoff/post-remove-saved.png`, and `template-handoff/small-saved-fixed.png`.

## Findings and Limits

The direct Start route is now a visible control and its handler reaches the existing workout-start gate. A full post-change template launch was not repeated after the final label-only change because the restored baseline intentionally sits at the trial limit; the same route was exercised before restoration. The active logging, exercise picker, and first-set state are observed only on the temporary local fixture, not a store build.

Do not claim full accessibility compliance or comprehension from these screenshots. The next product decision is whether persistent rest notifications should remain default-on and request Android permission during the first set, or become an explicitly enabled optional setting before a workout. No policy change was made in this pass.
